1
In the OpenMP Fork-Join execution model, why are worker threads not destroyed by the operating system kernel when reaching the join barrier?
  • (A) OpenMP compilers lack the system calls to destroy threads.
  • (B) Threads hibernate in a thread pool to eliminate repetitive OS kernel thread creation and context allocation overhead at subsequent parallel regions.
  • (C) Master Thread 0 terminates, leaving workers running.
  • (D) Operating system threads cannot be destroyed once spawned.
Answer: (B) Thread Pool Hibernation & Low Latency
• Why (B) is True: Spawning OS kernel threads via clone() or pthread_create() requires thousands of CPU cycles (allocating thread control blocks, kernel stack frames). By parking threads in a sleep/spin pool, subsequent #pragma omp parallel blocks awaken them in sub-microsecond time.
• Why others are false: OS kernels easily destroy threads; Master Thread 0 remains alive throughout.
2
How does the OpenMP clause reduction(+:sum) eliminate race conditions on shared variable sum without incurring massive mutual exclusion lock contention?
  • (A) By serializing the entire loop across the master thread.
  • (B) Each thread accumulates into a private local copy initialized to the operator identity (0), followed by a lock-free logarithmic tree reduction at the barrier.
  • (C) By flushing all L1 caches to DRAM on every iteration.
  • (D) By converting the loop into POSIX semaphores.
Answer: (B) Private Accumulators + Tree Reduction
• Why (B) is True: OpenMP allocates a thread-private variable for each worker initialized to identity (e.g. 0 for +, 1 for *). Threads accumulate locally without touching shared memory. At the join barrier, the runtime combines private values into the original shared variable via an O(log₂ p) tree reduction.
• Why others are false: It does not serialize execution (A); flushing cache lines causes catastrophic false sharing (C).
3
For a loop where iteration computational workload varies wildly (e.g., Mandelbrot set rendering), which OpenMP scheduling policy is optimal and why?
  • (A) schedule(static) because it has zero runtime queue overhead.
  • (B) schedule(dynamic, chunk) or guided because threads dynamically pull chunks from a shared work-queue, preventing idle processor waiting.
  • (C) schedule(runtime) because it disables compiler optimizations.
  • (D) No scheduling clause is permitted for non-uniform loops.
Answer: (B) Dynamic / Guided Work-Queue Balancing
• Why (B) is True: When iteration execution times vary unpredictably, static scheduling assigns heavy iterations to one core while others finish early and sit idle. dynamic scheduling allows fast threads to continuously pull new chunks, achieving balanced processor utilization.
• Why others are false: static suffers severe load imbalance; runtime simply delays selection to an environment variable.
4
Why is the OpenMP clause default(none) strongly recommended by expert high-performance computing engineers?
  • (A) It automatically parallelizes nested loops.
  • (B) It forces the programmer to explicitly declare the scoping (shared, private, firstprivate) of every variable, preventing catastrophic unintended data races.
  • (C) It allocates all variables on GPU device memory.
  • (D) It turns off compiler warnings.
Answer: (B) Enforcing Explicit Scoping to Eliminate Races
• Why (B) is True: By default, variables defined outside parallel regions are implicitly shared. If an inner temporary variable is accidentally left shared, multiple threads overwrite it concurrently, causing silent data corruption. default(none) makes the compiler reject any un-scoped variable at build time.
• Why others are false: It does not affect GPUs or loop nesting.
